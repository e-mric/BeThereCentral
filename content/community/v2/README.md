# Community content package v2

Version 2 is a declarative, bounded package for a fictional room and an optional small learning quest. It is independent from the current Compose map and does not represent a surveyed BeCentral room. `package-v2.json` is the room-only fixture; `package-play-learn-v2.json` preserves the manual-appearance contribution lesson; `package-founders-v2.json` demonstrates the Founder and Patch trusted presets. `package-ninon-v2.json` and `package-morgane-v2.json` demonstrate separately approved character names and presets with empty introductions. `package-architect-v2.json` demonstrates the approved self-character preset with an empty introduction. The v1 contract remains frozen and available at `../v1/`.

The root has exactly ten fields: `packageVersion` (2), `packageId` (`betherecentral.sample-room`), positive safe-integer `contentRevision`, an exact supported `features` array, `assets` (the catalog ID and revision), `attribution` (the catalog attribution ID), `room`, `characters`, `quest`, and `gameplay`. Unknown keys are rejected at every level. JSON object key order is immaterial; array order is significant. Text limits count UTF-16 code units, IDs are safe ASCII, coordinates and dimensions are safe integers, and the input is capped at 65,536 UTF-8 bytes before parsing.

`rooms-v2` packages have no characters or gameplay. `rooms-v2` + `play-learn-v1` requires exactly two characters, exactly two clue records, three answers and one `inspect-two-answer-one-v1` quest. Character appearance is either the exact seven-field manual enum record or the exact `{ "presetId": "founder-v1" }` trusted preset reference. Presets resolve only through `avatarPresets` in the bundled asset catalog; package content cannot supply sprite paths or metadata. `gameplay` links the player, guide and both clue locations by IDs. All positions use the fixed fictional 320 × 224 chamfered room coordinate system. The immutable polygon is copied from v1; it is not an actual room survey.

Props have `{id,kind,x,y,width,height}` fields. `kind` resolves against `../assets/catalog-v2.json`; crop, image, draw order, interaction and normalized collision footprint come only from that trusted catalog. Positions and dimensions must be integers, dimensions must meet catalog min/max bounds and all sprite corners must fit inside the room. There are at most 24 props. A bookshelf opens only the built-in `white-construct` scene, and a duck has only its built-in `debug-duck` interaction. Packages cannot request scripts, files, scenes or remote content.

Playable coordinates are standing centers on a four-pixel grid. A radius-six character must fit within the outline and outside catalog collision boxes expanded by its radius. Four-neighbour breadth-first reachability from spawn must connect the guide and both clue locations. The search must reach the bookshelf's front approach point (centered 8 pixels south of its footprint) and a point within 24 pixels of the debugging duck. This keeps built-in interactions reachable while allowing props at any integer coordinate. This conservative check supports the fictional room game; it does not create a real-building route or accessibility guarantee.

The v1 adapter first validates the complete legacy package, then upgrades only its room-compatible desk, plant, sofa and rug props. It does not create characters or gameplay. A legacy scene outside v2 catalog size or geometry limits fails with an explicit lossless-upgrade error. Quest progress is local pure state: both distinct clues and a correct answer are required; wrong answers keep clues, duplicate clue visits do nothing, rewards are granted once, and reset starts a new attempt. `validateProgress`, `serializeProgress` and `parseProgress` check saved state before it can be loaded; progress is separate from the content package.

Run `node --test content/community/v2/test/*.test.js` from the repository root. `acceptance.json` is the shared expected-validity list for matching the independent Godot validator. `node content/community/v2/test/acceptance-runner.js` emits the accepted packages normalized with sorted object keys, so the independent consumers can compare both acceptance and normalized data.

The [combined content gate](../../../game/README.md) now compares this report against Godot's independent v2 results as well as the separate v1 corpus: `python3 scripts/check_community_content.py --godot godot` from the repository root. It verifies that each manifest covers every example/invalid fixture, checks normalized accepted values and rejects incomplete or error-producing runs. It is also run by the hosted `community-content` job.
